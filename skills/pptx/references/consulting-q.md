# consulting-Q — MBB 級デッキの TPO 別プレイブック

`deck-types.md` が「ジャンルごとの違い」を決めるのに対し、このファイルは「コンサル系の資料を、会議の種類に合わせて、同じ品質で出す」ための実務ルールである。依頼が「コンサル品質」「経営会議向け」「役員が読む資料」のときはここから始める。語句・レイアウトの発想は公開資料から概念だけを吸収したもので、本文は本スキル向けに書き直している。数値の正本は `design-system.md` と `qa.md`、文体の土台は `content-rules.md` であり、矛盾したらそちらを優先する。

## 1. TPO 分類 — 相手と場面でデッキの型が変わる

まず「誰が・どこで・何を決めるか」を 3〜5 行で固定する（目的・成果物・スコープ IN/OUT・枚数）。その後に TPO を選ぶ。同じ分析でも、経営会議への答申と現場キックオフでは一枚あたりの情報量もトーンも別物になる。

| TPO | 読む／聞く | 求める判断 | 許容密度 | 枚数（本文） | トーン |
|---|---|---|---|---|---|
| 経営会議への答申 | 事前回覧で**読む**、会議で質疑。資料が主 | 承認／方針決定。反論できるだけの根拠 | 中。1 メッセージ＋比較表・数値・出典 | 12〜20＋付録。先頭 1 枚で答えを出す | 断定的・簡潔。不確実性は「仮説」と明示 |
| 現場キックオフ | その場で**聞く**、資料は補助 | 理解と今日からの行動 | 低。本文 18pt 以上、1 枚 3 点以内 | 8〜15。デモ／実物を 1 枚入れる | 具体的・前向き。抽象的な合言葉は禁止 |
| 提案ピッチ（7〜10 分） | **聞く**が主。資料は話のリズムを決める | 関心を持つ／次の会議を設定する | 低。1 枚 1 アイデア、大きな数字 1 つ | 7〜12（7 分なら 8〜10）。会社紹介は 1 枚まで | 課題→機会→自分たちの順。自慢を前置きしない |
| ステアリングコミッティ報告 | 事前回覧で**読む**、会議で例外だけ議論 | 進捗の承認／リスク対応の指示 | 中〜高。KPI・計画比・リスクの表が中心 | 10〜15＋詳細付録 | 事実優先。悪い知らせを先に置き、言い訳しない |
| 個人レビュー（1on1／上司レビュー） | 画面共有で**読む＋話す** | 優先順位の修正／次の一歩 | 低〜中。論点と仮説だけを並べる | 5〜8。結論のページで締める | 率直・仮説込み。「検討します」で終わらせない |

枚数は本文だけを数え、参照資料・計算過程・詳細データは付録に回す。全 TPO に共通して変えてはいけないのは「1 スライド 1 メッセージ」と「タイトルが結論」の 2 点だけである。読み手が一人で開く資料ほど自足性（出典・前提・用語定義）を強め、話し手が隣にいる資料ほど文字を削る。

## 2. consulting-Q の定義 — 「一流に見える」最低条件

“MBB quality” はセンスではなく、欠けると即座に指摘される条件の集合として扱う。下表の Must を 1 つでも満たさなければ納品しない。Should は TPO と時間に応じて調整する。

| # | 区分 | 最低条件 | 確認のしかた |
|---|---|---|---|
| 1 | Must | 全スライドのタイトルが主張文（action title）。「市場概要」のような見出し語は禁止 | タイトルだけを通し読みして意味が通るか |
| 2 | Must | 1 スライド 1 メッセージ。本文はそのタイトルの証明だけに使う | タイトルと本文の主張が 2 つ以上になっていないか |
| 3 | Must | 主張は issue tree → governing thought（答え 1 文）→ MECE な論拠 → 証拠のピラミッド | 論拠どうしが重複・漏れしていないか |
| 4 | Must | 証拠の直後に so what（だから何か・何を決めるか）を置く | 「重要です」で終わっていないか |
| 5 | Must | 装飾を排する。角丸・影・グラデーション・絵文字・多色使い・イコンの乱用なし | 全スライドを並べて装飾だけが目立たないか |
| 6 | Must | 数値・主張には出典行、全ページにページ番号 | 付録も含めて欠けがないか |
| 7 | Must | 本文ゾーンの余白は約 20%。詰め込みとスカスカの両方を避ける |  render 画像で空白の偏りを見る |
| 8 | Must | フォントは 1 種類（英数字の数字用 1 種を除く）。色数は実質 3 色以内 | タイトル位置・書体・色が全ページ同一か |
| 9 | Must | 本文 ≥ 14pt、外側余白 ≥ 0.5in、ブロック間 ≥ 0.3in | `lint_deck.py`＋目視（`qa.md` が正本） |
| 10 | Should | 冒頭 1 枚で結論と論点を一望できる（エグゼクティブサマリー） | 経営・ステコミでは Must に昇格 |
| 11 | Should | 比較は軸のある表、推移・構成比・分布はネイティブのチャート | カード羅列で済ませていないか |
| 12 | Should | 推奨・注意などの評価語には根拠と比較基準を添える | 基準のない「十分」「最小限」がないか |

色の配分はベース（白／淡灰）・メイン（紺など）・強調（朱など）の 3 色、強調は 1 スライド 1 要素まで。灰の濃淡で情報の重みを作り、意味を色だけに載せない（色覚多様性とモノクロ印刷の両方に効く）。

## 3. ストーリーライン先行プロセス

**スライドを作る前に、タイトル一覧を完成させる。** ここを飛ばすと、どれだけ体裁が整っても「綺麗なだけの資料」止まりになる。

1. **Define**：TPO・読み手・今日ほしい判断・スコープ IN/OUT・提出形式を 3〜5 行で書く。背景が薄いなら長いデッキではなく 1 枚の論点メモで合意を取る。
2. **Issue tree**：意思決定の問いを頂点に、答えるために必要な論点を木に分解する。枝は MECE にし、優先度の低い枝は切る（後で付録に回す）。
3. **Governing thought**：木を解いた答えを 1 文で書く。これがエグゼクティブサマリーと表紙の主張になる。
4. **タイトル一覧**：各スライドに「結論の 1 文」＋「見せ方（表／グラフ／2 カラム／数値／フロー）」を 1 行で書く。列を作ったら上から声に出して通し読みする。「だから」「しかし」で自然に繋がらない箇所は、スライドを作る前に並べ替えるか削る。
5. **証拠の割り当て**：各論拠にチャート・表・数値・引用を 1 つずつ対応させ、出典と so what を書き添える。ここで初めて 1 枚目の見本スライドを作り、全体に展開する前にレビューする。

ピラミッドの形は常に同じである。

```
問い（何を決めるか）
└─ Governing thought（答え 1 文）
   ├─ 論拠 1 → 証拠 → so what
   ├─ 論拠 2 → 証拠 → so what
   └─ 論拠 3 → 証拠 → so what
```

タイトル一覧の例（各文は前缀ではなく結論そのもの）：

- 受注単価の低下が、増収でも営業利益率を 1.8pt 押し下げている
- 値引きは 2 商材と商社経由案件に集中し、全案件の波及ではない
- 見積承認を現場に移せば、値引き率を 2 四半期で半減できる

3 行目で「だから何をするか」に着地していることを確認する。結論を最後のスライドまで取っておくのは、このピラミッドの逆をやっていることになる。

## 4. 日本語特有のルール

### 4.1 アクションタイトル

型は〔条件・対象〕＋〔結論〕＋〔根拠・数字〕。1 行 34 字以内、どうしても長ければ 2 行・64 字以内で、文節の切れ目で折る。句点は付けず、「について」「の件」「まとめ」「概要」「一覧」「とは」で終わらせない（全部ラベル）。動詞は「する／必要／超える／占める」などで言い切る。「〜と言える」「〜と考えられる」は責任回避なので、根拠が弱ければ「仮説：」と書く。

| 要素 | 文体 | 作り方 |
|---|---|---|
| 表紙タイトル | 体言止め | 資料の対象と文書種別だけを置く（方針（案）など） |
| アクションタイトル | 常体の言い切り | 結論＋根拠。句点なし、2 行まで |
| タイトル下のリード | 体言止め／常体 | 対象・条件・試算範囲を 1 行で補足（サブタイトルではない） |
| 箇条書き | 体言止めか動詞言い切り | 1 スライド内で語尾を統一する |
| ラベル・表セル | 名詞・数値 | 単位は列見出しに 1 回だけ書く |
| 出所・注 | 体言止め | 「出所：」「注：」で始める |
| スピーカーノート | です・ます可 | 話し言葉はここに置き、スライド本文に混ぜない |

丁寧さが求められる顧客向けでも、タイトルと箇条書きは常体のままにする。です・ますを許すのは表紙の副題と、明示的に指示されたリード文だけである。

### 4.2 AI 臭表現カタログ（型で拾う）

単語を差し替えるだけでは直らない。原因は「具体性がない」「責任をぼかす」「文書の文体をそのままスライドに流用する」「英語を直訳する」の 4 つで、直し方は共通して「誰が・何を・いくつ・いつまで」を足すか、行ごと削ることである。社名を差し替えても成立する文は空疎と判定する。

| 型 | 典型的な症状 | 直し方 |
|---|---|---|
| 空疎・万能語 | 「さまざまな」「適切に」「包括的な取り組み」「革新的な手法」 | 数か名前を列挙するか、数値・基準を添える。添えられなければ削る |
| 文末のぼかし | 「可能です」「重要だと言えるでしょう」「検討が必要です」 | 断定する。弱い主張なら「仮説：〜」と書いて検証条件を出す |
| 名詞止めの空洞化 | 「検討」「強化」「対応」「最適化」だけで終わる行 | 対象と成果を足す（何をいつまでに、何がどう変わるか） |
| 翻訳調・無生物主語 | 「〜を可能にする」「〜に焦点を当てる」「改善が実現される」 | 人・組織を主語にして日本語の動詞で言い直す |
| 硬い接続の反復 | 「〜において」「〜を踏まえ」「〜の観点から」が 1 枚に複数回 | 助詞か短い動詞に替える（「移行時に」「検証で」） |
| 構文の癖 | 「〜だけでなく〜も」「3 点セット」の自動生成、接続詞で始まる行 | 項目数は中身で決める。比較は数値で見せ、接続詞は削る |
| 体裁・記号 | 絵文字、✅、全角英数字、半角カナ、ASCII の「...」 | 記号は ● ▲ ※ ◎ ○ △ に限定。英数字は半角、省略記号は「…」 |
| 数値の雑さ | 「大幅に改善」「10000」「前年比 3% 改善（割合の差なのに %）」 | 「約 30% 減」「10,000」「前年比 +3pt」。比較対象と出所を必ず添える |

書き直しは 3 パスで機械的に進める。①削る（意味が変わらない接続詞・「〜という」を消す）→②足す（残った抽象語に対象・数値・期限を与える。与えられない行は消す）→③揃える（文末・粒度・用語・句読点を統一する）。1 枚の箇条書きは各ブロック 3〜5 項目、6 項目を超えたら表か図に変える。入れ子は 2 段まで。

### 4.3 禁則処理とフォント

- 「、。」「）」などが行頭に孤立せず、開き括弧が行末に残らないようにする。禁則設定（OOXML の `eaLnBrk` 等）が使えるならオンにし、レンダラが面倒を見ない場合はタイトルの改行位置だけ手動で決める。
- 日本語は角ゴシック 1 種に統一する。この環境で実測できるのは `BIZ UDGothic` と `Noto Sans JP`。`Yu Gothic` / `Meiryo` は LibreOffice プレビューで別フォントに置換され、字幅が変わってはみ出しの原因になる。これらを使う場合は text box に約 1 割の横余裕を取る。
- テーマの東アジアフォントを固定しないと PowerPoint 側で細い既定書体に差し替わる。生成側で指定できるなら明示する。
- 本文 14pt（読む資料）／18pt 以上（投影）。注・出所は 10pt 未満にしない。太字は見出しとラベルだけ、1 枚 2 か所まで。斜体・下線・文字影は日本語で字形が崩れるので使わない。

## 5. NG パターン集 — AI っぽいスライドの典型

| NG | なぜダメか | どう直すか |
|---|---|---|
| テンプレ文型の反復（毎枚「〜の現状と課題」） | 主張ではなく型が見え、タイトルを通し読みしてもストーリーにならない | 各枚の結論を 1 文で書き直し、文型を 3 種類以上に散らす |
| タイトル下のサブタイトル行 | 2 つ目の見出しができ、1 枚 1 メッセージが崩れる | 必要な条件はリード 1 行に統合するか、本文の注に移す |
| カードグリッド乱用（内容と無関係に 3 分割／2×2） | 関係のない項目を並べただけでは比較の軸が読めない | 比較なら行＝項目・列＝観点の表に、手順なら矢羽／フローに替える |
| 色だけのステータス（赤／黄／緑の丸だけ） | 意味が色に依存し、モノクロ印刷と色覚多様性で読めない | 色に加えて状態を文言で書き、凡例を同じスライドに置く |
| 装飾バー（タイトル下線、全幅ヘッダー帯、横端の色帯） | 情報を持たない線が視線を奪い、清潔さが失われる | 線を消し、余白・淡い塗り・文字の重みで構造を示す |
| 本文の中央揃え | 開始位置が揃わず、数行の比較ができない | 左揃えを基本にする。中央揃えは図形内の見出しだけに許す |
| 全スライド同じレイアウト | 重要度が均質化し、どこが結論か分からない | 主張の種類（比較・推移・構造・計画）ごとに骨格を替える |
| タイトルがラベル（「売上動向」「第 3 章」） | 読み手が自分で結論を組み立てる羽目になり、答申にならない | 「何がどうなった／だから何をする」を 1 文で入れる |

どれも「見た目の問題」に見えるが、実際には文章と論理の問題である。レイアウトを替える前にタイトルと論拠を書き直す。

## 6. 機械チェックと人間のレビュー

### 6.1 `lint_deck.py` が拾えるもの

```bash
python3 skills/pptx/scripts/lint_deck.py out.pptx
python3 skills/pptx/scripts/lint_deck.py out.pptx --pdf render/out.pdf   # 描画後の語 box も検査
```

- 拾える：極端に小さい図形（tiny-extent）、画面外・文字の端部接触（off-canvas）、外側余白 < 0.5in（margin）、図形の重なり（overlap）、0.3in 未満の狭い間隔（tight-gap）、フォントの許容リスト外（font）、文字量に対する枠の高さ不足の概算（text-overflow）、空のテキスト枠、`lorem` / `TODO` などのプレースホルダー、画像の低解像度（< 96dpi）、`--pdf` 時のページ端を越える語のbox。
- 拾えない：action title かどうか、1 枚 1 メッセージ、MECE／ピラミッド、so what の有無、AI 臭い言い回し、禁則、タイトルと図の結論の食い違い、ページ間の数値不一致、出典行の欠落、意味が色だけに載っていること、色数、実際の改行位置。text-overflow は文字数からの概算なので、確定判定には render 画像と `--pdf` が必要。

フォントのデフォルト許容リストには `Calibri` / `Cambria` / `Arial` / `BIZ UDGothic` / `Noto Sans JP` が含まれる。其他の書体を使う場合は意図して `--fonts` を渡す（警告を消すためではなく、書体を固定するため）。

### 6.2 タイトル一覧の抽出と通し読み

markitdown はスライドごとに区切りコメントを出すので、その直後の非空行をタイトルとして抜く。

```bash
markitdown out.pptx | awk '/^<!-- Slide number:/ {want=1; next} want && NF {print; want=0}'
```

環境に markitdown が無いときは python-pptx で各スライド最初の非空テキストを出す（同じ順序で読めればよい）。

```bash
python3 - <<'PY'
from pptx import Presentation
for i, s in enumerate(Presentation("out.pptx").slides, 1):
    t = next((sh.text.strip() for sh in s.shapes if sh.has_text_frame and sh.text.strip()), "(no title)")
    print(f"{i:02d}: {t}")
PY
```

抜いた一覧を上から読み、「話が飛ぶ／戻る／同じことを二度言う／前提なしに結論が出る」がないかを見る。ここで直る問題は、スライド本文を触るよりずっと安い。

### 6.3 フレッシュアイ・レビューの依頼例

作り手は自分の意図を見るので自分の欠陥に気づかない。文脈を共有していない別エージェントか新しいセッションに、作り方・規約・テンプレートを見せずにデッキだけを渡す。以下はそのプロンプト例である（{N} と {FILE} を置き換える）。

```
あなたは {N} 枚のプレゼン資料のレビュアーです。ファイル {FILE} の全ページを順に読み、
作り手には見えない破綻を指摘してください。生成方法や規約は教えられません。推測して
説明する必要はありません。まず確認項目を見る前に、読み手として一番困る点を 3〜10 件、
思いつくまま書いてください。次にページ番号付きで以下を報告してください。
- 日本語: 不自然な言い回し、語尾の不統一、定義なしの略語、同じ概念の表記ゆれ
- 論理: タイトルだけを通し読んだときの飛躍・重複・前提なき結論
- 破綻: タイトルの数と本文の数の不一致、タイトルと図の結論の不一致、根拠のない
  評価語、既出ページの焼き直し、目次と本編のずれ、ページ間の数値不一致、
  出典の欠落、何を読み手に決めてほしいかの欠落
各指摘は「ページ番号／該当箇所の引用／何が問題か／言い換え案」の 4 点で書く。
最後に、ストーリー・1枚1メッセージ・情報構造・版面・説得力・一貫性・誠実さを
それぞれ 10 点で採点し、直すべき上位 5 件をインパクト順に挙げてください。
欠点が 3 つ見つからなければ「見つからなかった確認項目」を明示してください。
```

返った指摘は「採用／不採用／保留＋理由」の採否表にし、採用分だけ直してから機械チェックと render を再実行する。指摘を丸呑みしてストーリーを壊さないこと。

## 7. TPO 別クイックリファレンス

`type` 名は outline JSON スキーマの例である。基本型は `title` / `section` / `bullets` / `stats` / `chart` / `table` / `closing`、用途別の拡張型として `exec_summary` / `kpi_row` / `axis_table` / `premise_conclusion` / `issue_action` / `chevron_flow` / `status_heatmap` / `two_by_two` / `bridge` / `recommendation` がある（未対応の環境では基本型の `bullets` / `stats` / `chart` / `table` に読み替える）。推移は `chart.kind: "line"`、増減の分解は `bridge`（または `chart.kind: "waterfall"`）を使う。パレットは `consulting` を優先する。

| 会議 | 推奨 type の並び | 密度 | 枚数 | 必須要素 |
|---|---|---|---|---|
| 経営会議への答申 | title → exec_summary → bridge／axis_table → status_heatmap → recommendation | 中 | 12〜20＋付録 | 1 枚目の答え、比較軸、出典、決定事項とオーナー |
| 現場キックオフ | title → section → chevron_flow → issue_action → closing | 低 | 8〜15 | 今日からの行動、担当・期限、デモ／実物、18pt 以上 |
| 提案ピッチ | title → bullets（課題） → kpi_row → two_by_two → recommendation | 低 | 7〜12 | 定義文、比較の前提、試算は「想定」と明記、次の依頼 |
| ステアリングコミッティ | title → kpi_row → chart（推移） → status_heatmap → issue_action → closing | 中〜高 | 10〜15＋付録 | 進捗の状態、計画比、リスクと対応者、今回の決定事項 |
| 個人レビュー | title → issue_action → axis_table → recommendation | 低〜中 | 5〜8 | 論点の絞り込み、仮説と根拠、次の一歩と期限 |
